# Scalo — spécification

Plateforme tout-en-un : **funnel builder**, **emails** (newsletters + campagnes automatiques), **contacts** (CRM + tags).

## Architecture

```
shared/  @scalo/shared — types TS, rendu HTML des blocs (renderBlock, renderPageDocument, renderEmailDocument), templates
api/     Express 5 + PostgreSQL (Kysely + pg) + JWT, port 4000. Sert aussi les pages publiques des funnels (SSR) et le tracking email.
web/     React 19 + Vite + Tailwind v4 + react-router, port 5173. Proxy Vite: /api, /p, /t, /u, /c, /m, /a, /uploads, /oauth/(authorize|token|revoke|introspect), /.well-known -> http://localhost:4000
ee/      Édition Entreprise (licence commerciale, optionnelle) : équipe et rôles, journal d'audit, marque blanche. Chargée à l'exécution par api/src/ee.ts et web/src/lib/ee.ts si le dossier existe — voir « Éditions ».
```

Tous les packages sont ESM + TypeScript. `@scalo/shared` est importé en source TS (`import { renderPageDocument } from '@scalo/shared'`).
L'API tourne avec `tsx`. Le contenu d'une page ou d'un email est toujours un `PageContent` (`{ settings, blocks }`) stocké en `jsonb`.

### Base de données (PostgreSQL)

- **Accès** : `api/src/db/index.ts` (pool `pg` — 10 connexions par défaut, `statement_timeout` 15 s, `idle_in_transaction_session_timeout` 30 s — et instance Kysely `db`), schéma typé dans `api/src/db/schema.ts`. Requêtes via le query builder Kysely ; le tag `sql` n'est utilisé que pour les agrégats (statistiques, file d'envoi, dashboard) et toujours avec des paramètres liés, jamais de concaténation d'entrées utilisateur.
- **Conversions à la frontière** (parseurs `pg`) : `bigint` → `number` (ids, `COUNT(*)`), `timestamptz` → chaîne ISO (`toISOString()`), `jsonb` → objet. Les booléens (`unsubscribed`, `bounced`) restent exposés en `0 | 1` par l'API ; `smtp_secure` en booléen. Le contrat HTTP est inchangé.
- **Migrations versionnées** : `api/src/db/migrations/000N_*.ts` (`up`/`down`), enregistrées dans `api/src/db/migrate.ts` (Kysely `Migrator`, fournisseur statique, historique dans `kysely_migration`, verrou contre les exécutions concurrentes). `npm run migrate`, `npm run migrate:down`, et au démarrage de l'API si `AUTO_MIGRATE` (défaut : oui hors production). Démarrage refusé avec un message clair si la base est injoignable.
- **Schéma** (`0001_init`) : ids `bigint generated always as identity` ; dates `timestamptz` ; contenus / accès / données d'événement en `jsonb` ; énumérations en `CHECK` (`steps.type`, `steps.access->>'mode'`, `broadcasts.status`, `email_sends.status`, `contact_events.type`) ; emails stockés en minuscules (`CHECK (email = lower(email))`) ; noms de tags uniques sans casse (`UNIQUE (user_id, lower(name))`) ; `UNIQUE (user_id, email)` contacts, `UNIQUE (slug)` funnels, `UNIQUE (funnel_id, slug)` étapes, `UNIQUE (campaign_id, contact_id)` inscriptions, `UNIQUE (step_id, visitor_id)` vues (`ON CONFLICT DO NOTHING`). Clés étrangères `ON DELETE CASCADE` vers le compte / parent, `SET NULL` pour les références optionnelles (tag d'une newsletter, déclencheur de campagne, source d'un envoi, funnel/étape d'un événement). Index pour chaque requête chaude (file d'envoi `(status, send_at)` et `(user_id, status, send_at)`, outbox `(user_id, id desc)`, envois récents partiel `WHERE status='sent' AND NOT is_test`, timeline `(contact_id, created_at desc)`, stats `(funnel_id, type)` / `(step_id, type)`, dashboard `(user_id, type, created_at)`…).
- **Schéma** (`0002_oauth`, historique — annulé par 0004) : `users.password_hash` nullable (comptes créés via OAuth) ; `user_identities` (`provider` en `CHECK ('google','github')`, `UNIQUE (provider, provider_user_id)`, `UNIQUE (user_id, provider)`, email en minuscules) ; `auth_login_codes` et `auth_link_tickets` (secret à usage unique stocké en SHA-256, `expires_at`, `used_at`, consommé par `UPDATE … WHERE used_at IS NULL AND expires_at > now() RETURNING`) ; `auth_attempts` (`key` PK, `count`, `window_start` : compteurs de limitation incrémentés par un upsert atomique). Le `down` remplace les `password_hash` NULL par un marqueur inutilisable avant de remettre `NOT NULL`.
- **Schéma** (`0003_email_features`) : `settings.double_optin_default`, `settings.webhook_secret` (unique, généré à la première lecture), `settings.dkim_selectors` ; `contacts.confirmed_at` (NULL = double opt-in non confirmé ; les contacts existants reçoivent `created_at`, défaut `now()`), `contacts.confirmation_sent_at`, `contacts.complained` ; `broadcasts.status` ∈ `draft|scheduled|sent` + `scheduled_at` (`CHECK status <> 'scheduled' OR scheduled_at IS NOT NULL`), `ab_test jsonb`, `ab_phase` (`testing|done`), `ab_winner`, `ab_decide_at` ; `campaigns.stop_tag_id` ; `campaign_emails.condition jsonb` ; `campaign_subscriptions.status` (`active|completed|stopped|unsubscribed`), `stopped_at`, `stopped_reason` ; `email_sends.kind` (`broadcast|campaign|test|confirmation`, rempli pour l’existant), `variant`, `message_id`, `complained_at`, statut `skipped` ; index uniques partiels `(campaign_email_id, contact_id)` et `(broadcast_id, contact_id)` hors tests (jamais deux fois le même email) ; table `pending_optins` (SHA-256 du jeton, actions en attente, `expires_at`, `confirmed_at`) ; nouveaux types d’événements. Le `down` repasse les newsletters programmées en brouillon, les envois `skipped` en `failed`, supprime les événements des nouveaux types.
- **Schéma** (`0004_oauth_provider`) : supprime `user_identities`, `auth_login_codes`, `auth_link_tickets` et remet `users.password_hash` `NOT NULL` (échoue avec un message clair s’il existe des comptes sans mot de passe) ; `auth_attempts` conservée. Serveur d’autorisation OAuth 2.0 : `oauth_clients` (`client_id` unique, propriétaire `user_id` → users `CASCADE`, `type` `confidential|public`, `secret_hash` SHA-256 + `secret_hint`, `CHECK ((type='confidential') = (secret_hash IS NOT NULL))`, `redirect_uris text[]` 1–10, `scopes text[]` ⊆ liste des scopes, `logo_url ~ '^https://'`) ; `oauth_authorization_requests` (`id_hash` PK = SHA-256 de l’id, client `CASCADE`, `redirect_uri`, `scopes`, `state`, `code_challenge` + méthode `S256`, `prompt_consent`, `expires_at` 10 min, `consumed_at`) ; `oauth_codes` (`code_hash` PK, client/user `CASCADE`, `redirect_uri`, `scopes`, `code_challenge`, `family_id uuid`, `expires_at` 60 s, `used_at`) ; `oauth_tokens` (`token_hash` unique, `type` `access|refresh`, `family_id`, `parent_id` → oauth_tokens `SET NULL`, client/user `CASCADE`, `scopes`, `expires_at`, `rotated_at` (refresh uniquement), `revoked_at`, `last_used_at` ; index famille, (user, client), expiration) ; `oauth_consents` (PK (user, client), `scopes` = union des scopes accordés, `last_used_at`). Le `down` recrée les tables de 0002 (vides) et rend `password_hash` nullable.
- **Schéma** (`0005_automations_crm`) : `custom_fields` (compte `CASCADE`, `key` `^[a-z][a-z0-9_]{0,39}$` unique par compte, `label` 1–80, `type` `text|number|date|select|checkbox`, `options text[]` ≤ 100, `position`) ; `contacts.fields jsonb` (objet, défaut `{}`) ; `segments` (`name` unique sans casse par compte, `filter jsonb`, `updated_at`) ; `broadcasts.segment_id` → segments `SET NULL` ; `automations` (`trigger_type` en `CHECK` + `trigger jsonb` cohérent, `conditions jsonb` nullable, `actions jsonb` ≤ 20, `enabled`, `run_once`, `webhook_token` unique (URL secrète du webhook entrant), `signing_secret` (HMAC des webhooks sortants) ; index partiel `(user_id, trigger_type) WHERE enabled`) ; `automation_runs` (automatisation `CASCADE`, contact `SET NULL`, `status` `pending|running|waiting|completed|failed|skipped`, `step` = prochaine action, `chain bigint[]` + `depth` (anti-boucle), `trigger_data`, `log jsonb`, `error`, `resume_at` (`CHECK` : requis en `pending|waiting`), `claimed_by`/`claimed_at` ; index file `(resume_at, id) WHERE status IN ('pending','waiting')`, journal par automatisation / compte, `(automation_id, contact_id)`) ; index `contact_events (contact_id, type, created_at desc)` et activité email par contact ; types d’événements `purchase`, `campaign_completed` ; scope OAuth `purchases:write`. - **Schéma** (`0007_payments`) : `payment_settings` (PK `user_id` `CASCADE`, `stripe_secret_key` et `stripe_webhook_secret` **chiffrés** + `*_hint` (4 derniers caractères), `stripe_publishable_key`, `mode` `test|live`, `webhook_token` unique (partie secrète de l’URL du webhook), `account_name`, `verified_at`) ; `products` (`name` 1–200, `description`, `image_url`, `tag_id` → tags `SET NULL`, `campaign_id` → campaigns `SET NULL`, `revoke_on_refund`, `archived`) ; `product_prices` (offres : `type` `one_time|subscription|installments`, `amount` en centimes 50–99 999 999, `currency` 3 lettres minuscules, `interval` `month|year`, `installments` 2–36, `tax_rate numeric(5,2)`, `tax_inclusive`, `active` ; `CHECK` de cohérence type / interval / installments) ; `orders` (contact / tunnel / étape / commande parente `SET NULL`, `kind` `checkout|upsell`, `status` `pending|paid|failed|refunded|canceled`, `subscription_status` `active|past_due|canceled|completed`, `livemode`, montants entiers `amount_subtotal|tax|total|paid|refunded`, identifiants Stripe (session unique, payment intent, customer, payment method, subscription), `attribution jsonb`, `visitor jsonb`, `failure_message`, `paid_at` (`CHECK` : requis si payée / remboursée), `refunded_at`) ; `order_items` (instantané : noms, type, TVA, montants, `tag_id`, `campaign_id`, `revoke_on_refund`, `kind` `main|bump|upsell` ; produit / offre `SET NULL`) ; `order_transactions` (`type` `payment|refund`, `amount`, `stripe_id` unique par compte = clé d’idempotence, `stripe_payment_intent_id`) ; `stripe_events` (PK `(user_id, event_id)`). Type d’envoi `order` et scope OAuth `sales:read` : les `CHECK` `email_sends.kind` et `oauth_clients.scopes` sont reconstruits à partir de leurs valeurs actuelles. Le `down` supprime les tables, les envois `order` et retire le scope.
- **Schéma** (`0012_affiliates`) : `affiliate_programs`, `affiliates`, `affiliate_commission_rules`, `affiliate_clicks`, `affiliate_referrals`, `affiliate_commissions`, `affiliate_payouts` ; types d’événements `affiliate_joined` / `affiliate_commission` et déclencheur d’automatisation `affiliate_approved` (`CHECK` reconstruits à partir de leurs valeurs actuelles) — détail dans « Affiliation ».
- **Transactions** : `db.transaction().execute(async (trx) => …)` ; les services (`services/contacts.ts`, `services/email.ts`) prennent un exécuteur optionnel (`db` ou `trx`) et se composent dans une transaction (`inTx`). Les courses sont tranchées par les contraintes : upsert de contact atomique (`ON CONFLICT … DO UPDATE`), get-or-create de tag, `ON CONFLICT DO NOTHING` pour tags de contact / inscriptions / vues, passage `draft → sent` conditionnel d'une newsletter (un double clic ne met jamais en file deux fois). Une violation d'unicité (23505) non prévue répond 409, une clé étrangère (23503) 404, un `CHECK` 400, une base indisponible / un timeout 503.
- **Seed** : `npm run seed` (idempotent), `npm run seed -- --reset` (`TRUNCATE … RESTART IDENTITY`, refusé en production).
- **Tests** : `npm test` — `node:test` via tsx contre `TEST_DATABASE_URL` (base créée si absente, migrée, vidée au début de chaque fichier), app construite par `createApp()` (`api/src/app.ts`) sur un port éphémère, serveur SMTP factice pour les erreurs de livraison ; `oauth-provider.test.ts` pilote le flux OAuth complet avec fetch (autorisation, consentement, jetons, API v1).

## Conventions API

- Préfixe `/api`, JSON, auth `Authorization: Bearer <jwt de session>` (sauf `/api/auth/register|login` publics). `/api/v1/*` : API publique authentifiée par un jeton d’accès OAuth (voir plus bas), le JWT de session y est refusé.
- Erreurs : status HTTP + `{ "error": "message lisible en français" }`. 400 validation (zod), 401 non authentifié, 404 introuvable, 409 conflit, 429 trop de tentatives (+ `Retry-After`).
- Toutes les données sont isolées par `user_id` (multi-tenant).
- Dates : chaînes ISO (`new Date().toISOString()`), stockées en `timestamptz`.
- Les types de réponse correspondent à `shared/src/types.ts`.
- **Front servi par l’API** (`api/src/routes/spa.ts`, monté en dernier dans `app.ts`) : si `WEB_DIST` est défini — ou, en production, si `web/dist` existe — l’API sert le build Vite : fichiers statiques (`/assets/*` hachés : `immutable`, 1 an ; autres : 1 h), et `index.html` (`no-cache`) pour toute requête `GET` / `HEAD` qui n’est ni un fichier ni un chemin serveur. Chemins serveur, jamais remplacés par l’application (404 s’ils n’existent pas) : `/api`, `/p`, `/t`, `/u`, `/c`, `/m`, `/a`, `/uploads`, `/mcp`, `/.well-known`, `/oauth/authorize|token|revoke|introspect`. `/oauth/consent` reçoit `X-Frame-Options: DENY` + `frame-ancestors 'none'`. Un hôte de domaine personnalisé ou inconnu ne reçoit jamais l’application (`customDomainMiddleware` répond avant). Rien n’est servi en développement ni en test (Vite s’en charge). Déploiement Docker : `docs/self-hosting.md`.

### Fournisseur OAuth 2.0 (applications tierces)

Serveur d’autorisation RFC 6749 : *authorization code* + *refresh token* uniquement (pas d’implicit / password / client_credentials), PKCE RFC 7636 (S256 seul ; obligatoire pour les clients publics), révocation RFC 7009, introspection RFC 7662, métadonnées RFC 8414, paramètre `iss` RFC 9207, recommandations RFC 9700. Émetteur = `PUBLIC_URL`. Code : `api/src/services/oauth-server.ts`, `api/src/routes/oauth.ts` (protocole), `api/src/routes/oauth-account.ts` (écran de consentement, applications connectées, développeurs), `api/src/routes/v1.ts` (API publique). Scopes et textes du consentement : `shared/src/oauth.ts`.

Secrets : 32 octets aléatoires base64url préfixés (`scalo_app_` id client (12 octets hex), `scalo_cs_` secret, `scalo_ar_` demande, `scalo_ac_` code, `scalo_at_` accès, `scalo_rt_` refresh), seul le SHA-256 est stocké. Durées : demande 10 min, code 60 s, accès 1 h, refresh 30 jours (glissant par rotation).

| Méthode | Route | Entrée | Réponse |
|---|---|---|---|
| GET | /.well-known/oauth-authorization-server | | métadonnées RFC 8414 (CORS `*`) |
| GET | /oauth/authorize | `response_type=code, client_id, redirect_uri, scope, state?, code_challenge?, code_challenge_method=S256, prompt=consent?` | 1) `client_id` inconnu / `redirect_uri` absente ou non enregistrée (comparaison exacte) / paramètre répété → **page HTML 400** (jamais de redirection ; `X-Frame-Options: DENY`, CSP `frame-ancestors 'none'`, `no-store`). 2) autres erreurs → 302 `redirect_uri?error=…&error_description&state&iss` (`unsupported_response_type`, `invalid_scope` : absent / inconnu / non autorisé pour le client, `invalid_request` : PKCE manquant pour un client public, méthode ≠ S256, challenge mal formé, paramètre répété, state > 1000). 3) sinon demande stockée → 302 `PUBLIC_URL/oauth/consent?request=scalo_ar_…` |
| POST | /oauth/token | form (ou JSON) `grant_type=authorization_code, code, redirect_uri, code_verifier?` \| `grant_type=refresh_token, refresh_token, scope?` ; client : Basic, `client_id`+`client_secret` dans le corps, ou `client_id` seul (public) | `{access_token, token_type:'Bearer', expires_in:3600, refresh_token? | POST | /oauth/revoke | `token, token_type_hint?` + authentification client | 200 vide dans tous les cas (jeton inconnu ou d’un autre client : sans effet). Refresh → toute la famille révoquée ; accès → ce jeton seulement. CORS `*` |
| POST | /oauth/introspect | `token` + client **confidentiel** | `{active:false}` ou `{active:true, scope, client_id, username, sub, token_type, exp, iat, iss}` — uniquement pour les jetons du client appelant ; client public → 401. 300 / min |

Règles de `/oauth/token` : le code est verrouillé (`FOR UPDATE`) et marqué utilisé **avant** les autres vérifications (et la marque est conservée même si elles échouent) ; code déjà utilisé → `invalid_grant` + révocation de tous les jetons de sa famille ; client différent, expiré, `redirect_uri` différente, `code_verifier` manquant / faux (ou envoyé sans challenge) → `invalid_grant`. Refresh : jeton inconnu / d’un autre client / révoqué / expiré → `invalid_grant` ; déjà échangé (`rotated_at`) → **réutilisation** : famille révoquée + `invalid_grant` ; `scope` demandé ⊄ scopes d’origine → `invalid_scope` ; sinon rotation (`rotated_at`, nouveau refresh avec les scopes d’origine, nouvel accès avec les scopes demandés). Scopes effectifs = scopes du jeton ∩ scopes actuels de l’application.

### API publique (v1)

`/api/v1/*`, `Authorization: Bearer scalo_at_…` (RFC 6750). Sans jeton → 401 + `WWW-Authenticate: Bearer realm="scalo"` ; jeton invalide / expiré / révoqué (ou JWT de session) → 401 `invalid_token` ; scope manquant → 403 `{error:'insufficient_scope', scope}` + `WWW-Authenticate: Bearer error="insufficient_scope", scope="…"`. 120 requêtes / min par autorisation (application + compte ; un jeton rafraîchi partage le compteur) : `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset` (s), 429 `rate_limited` + `Retry-After`. `last_used_at` du jeton et du consentement mis à jour au plus une fois par minute. CORS `*` (sans cookies). Erreurs métier : `{error: "message"}` comme le reste de l’API.

### Serveur MCP (Model Context Protocol)

`POST /mcp` (hors `/api`) : transport **Streamable HTTP** du SDK officiel `@modelcontextprotocol/sdk`, sans état (un serveur par requête, réponses JSON, `GET`/`DELETE` → 405), CORS `*`. Authentification par les **jetons d’accès OAuth** (`Authorization: Bearer scalo_at_…`) : sans jeton → 401 + `WWW-Authenticate: Bearer realm="scalo", resource_metadata="<PUBLIC_URL>/.well-known/oauth-protected-resource"` ; jeton invalide / expiré / révoqué (ou JWT de session) → idem avec `error="invalid_token"`. `GET /.well-known/oauth-protected-resource` (et `…/mcp`, RFC 9728) → `{resource: <PUBLIC_URL>/mcp, authorization_servers: [<PUBLIC_URL>], scopes_supported, bearer_methods_supported: ['header']}`. Pas d’enregistrement dynamique de client : l’utilisateur crée une application dans Développeurs (redirection `https://claude.ai/api/mcp/auth_callback` pour Claude) ; le paramètre `resource` (RFC 8707) est accepté et ignoré par `/oauth/authorize`.

Chaque outil vérifie son scope (sinon résultat `isError` « Scope « … » requis ») puis appelle **l’endpoint `/api/v1` correspondant** sur le serveur lui-même (boucle locale, même jeton) : validation, isolation par compte, règles métier et limite de 120 requêtes / min sont celles de l’API publique, sans logique dupliquée (`routes/mcp.ts`). Les erreurs de l’API reviennent en erreur d’outil (`Erreur 404 : Contact introuvable`).

Code : `api/src/services/{fields,segments,bulk,automations,contact-actions,webhook-http}.ts`, `api/src/routes/{crm,automations,v1-crm}.ts`, types `shared/src/crm.ts`.

**Champs personnalisés** — définitions par compte (`key` stable `^[a-z][a-z0-9_]{0,39}$`, générée depuis le libellé si absente ; `email|first_name|last_name|phone|tags` réservées ; 50 max ; `key` et `type` immuables), valeurs dans `contacts.fields`. - **Déclencheurs** (`trigger`) : `optin {funnel_id?, step_id?}` (soumission sans double opt-in, ou confirmation du double opt-in) ; `contact_created` (formulaire, import, ajout manuel, API, webhook) ; `tag_added {tag_id}` ; `tag_removed {tag_id}` ; `link_clicked {url_contains?, broadcast_id?, campaign_id?}` (clic suivi `/t/c/…`, sans casse) ; `purchase {product?}` ; `campaign_completed {campaign_id?}` (inscription passée à `completed` ; nouvel événement `campaign_completed`) ; `course_completed {course_id?}` (toutes les leçons publiées d’une formation terminées, une seule fois par contact et par formation — voir « Formations et espace membres ») ; `affiliate_approved` (le contact devient affilié approuvé : inscription ouverte, validation d’une demande, ajout manuel ; une fois par affilié — voir « Affiliation ») ; `webhook` (URL secrète `hk_…`).
- **Branchement** : `logEvent` appelle `onContactEvent` qui met en file (`automation_runs`, `pending`) les automatisations actives dont le déclencheur correspond, **dans la transaction de l’appelant** (rien n’est créé si elle est annulée ; aucune action n’y est exécutée). `tag_added/removed` portent maintenant `tag_id` dans leurs données, `email_clicked` `broadcast_id` / `campaign_id`. La règle historique « tag → campagne » (`campaigns.trigger_tag_id`) est inchangée.
- **Exécution** (worker, à chaque tick, en parallèle des envois) : réservation atomique des exécutions dues (`pending`, ou `waiting` dont `resume_at` est passé) par `UPDATE … WHERE id IN (SELECT … FOR UPDATE SKIP LOCKED)` → `running` + `claimed_by`. Automatisation désactivée → `skipped` ; contact supprimé → `failed`. **Conditions** (un `SegmentFilter`) évaluées au démarrage (étape 0) : non remplies → `skipped`. **Actions** dans l’ordre : `add_tag`, `remove_tag`, `enroll`, `unenroll`, `set_field {key, value}`, `unsubscribe`, `webhook {url}`, `wait {amount 1–365, unit minutes|hours|days}` (→ `waiting` + `resume_at`). Chaque action de base de données et l’avancement de `step` (+ journal) se font dans **la même transaction**, vérifiée contre la réservation : exactement une fois, même après un crash. Une action impossible (tag / campagne / champ supprimé) → `failed` avec l’erreur, actions suivantes non exécutées. Les modifications d’une automatisation s’appliquent aux exécutions en attente.
- **Reprise** : les exécutions `running` d’une instance sans battement depuis 30 s (`worker_instances`) repartent en `pending` à leur étape (au démarrage puis toutes les 30 s).
- **Boucles** : les actions s’exécutent dans un contexte (`AsyncLocalStorage`) portant la chaîne des automatisations ; un déclenchement depuis ce contexte hérite de la chaîne. Une automatisation déjà présente dans la chaîne pour le même contact n’est pas redéclenchée ; au-delà de 5 niveaux la chaîne s’arrête. Les deux cas sont journalisés (`skipped`). `run_once` : au plus une exécution (non ignorée) par contact.
- **Webhook sortant** : `POST` JSON `{event: 'automation.webhook', delivery_id, automation: {id, name}, trigger: {type, …}, contact: Contact, sent_at}`, en-têtes `X-Scalo-Signature: t=<unix>,v1=<hex HMAC-SHA256(signing_secret, "<t>.<corps>")>`, `X-Scalo-Delivery` (stable `run.étape` : un appel rejoué après une reprise garde le même id — au moins une fois), `X-Scalo-Event`, `User-Agent: Scalo-Webhooks/1.0`. **SSRF** : `https` uniquement, pas d’identifiants dans l’URL, `localhost` / `.local` / `.internal` refusés ; le nom est résolu et **toutes** les adresses doivent être publiques (loopback, privées RFC 1918, CGNAT, lien-local dont `169.254.169.254`, multicast, réservées, IPv6 ULA / lien-local, IPv4 mappées / NAT64 / 6to4 refusées) ; la connexion est épinglée sur l’adresse validée (pas de DNS rebinding) ; délai 5 s ; redirections non suivies (3xx = échec) ; réponse ignorée (64 Ko lus au plus) ; 2xx = succès, sinon `failed` sans nouvel essai automatique. DNS et transport injectables en test (`setWebhookDeps`).
- **Achats** : pas de paiement dans l’app ; `POST /api/v1/purchases` ou webhook entrant avec `product` → événement `purchase {product, amount, currency, external_id, source}` (idempotent sur `external_id` par contact), qui déclenche les automatisations « Achat ».

Analyse tolérante (orthographes camelCase / snake_case, `fields` en tableau `{slug, value}` ou en objet, tags `{name}` ou chaînes). **Débit** : 429 → la tâche dort jusqu’à `Retry-After` (secondes ou date HTTP), à défaut `X-RateLimit-Refill`, à défaut 10 s (bornes 1 s – 15 min) ; `X-RateLimit-Remaining: 0` → pause avant la page suivante. 401 / 403 → tâche `failed`. Erreur réseau / 5xx → nouveaux essais espacés (5 s × 2ⁿ, 6 au plus), progression conservée. La clé ne part que vers `api.systeme.io`, n’est jamais journalisée ni renvoyée par l’API, est chiffrée dans `import_jobs.secret_enc` et effacée à la fin (succès, échec, annulation). `fetch` injectable (`setSystemeIoFetch`).
- **Exécution** (worker, à chaque tick) : réservation `pending → running` par `FOR UPDATE SKIP LOCKED` ; lots de 200 lignes (CSV) ou d’une page (API) ; **une transaction par lot** écrit les contacts, les compteurs, le journal **et le curseur**, gardée par la réservation (`WHERE claimed_by = moi AND status = 'running'`) : exactement une fois, même après un crash. Une tâche rend la main après 4 s (re-réservée au tick suivant). `running` d’une instance sans battement depuis 30 s → `pending` (`recoverImportJobs`, au démarrage puis toutes les 30 s). Annulation : le lot en cours est annulé par sa garde, ce qui était importé reste. Si un lot échoue en base, il est rejoué ligne par ligne et seule la ligne fautive est journalisée.
- **Règles par contact** : `upsertContact` (événement `imported` ; `created_at` d’origine pour un nouveau contact, un contact existant garde la sienne ; `keep_existing` → seules les valeurs vides sont complétées) ; champs personnalisés validés en mode tolérant (valeur invalide = avertissement au journal) ; désinscrit / bounce de la source appliqués (`unsubscribed` + séquences arrêtées, `flagBounce`) et **jamais** de réinscription d’un contact déjà désinscrit ; nouveaux contacts confirmés (l’utilisateur atteste le consentement), sauf ceux en attente de double opt-in ; tag d’import + tags de la ligne ; doublon d’email dans un même lot ignoré (avertissement), email vide = ignoré, email invalide = erreur.
- **Déclencheurs** : par défaut (`options.trigger = false`) le lot s’exécute dans `withTriggersSuspended` (`AsyncLocalStorage`) : `logEvent` écrit la timeline sans mettre d’automatisation en file, `addTag` n’inscrit pas aux campagnes déclenchées par le tag (le tag d’arrêt, lui, reste appliqué). Aucun email ne part d’un import. Avec `trigger: true`, comportement normal.
- **Page par URL** (`services/page-import.ts`) : `https` uniquement, port 443, pas d’identifiants, `localhost` / `.local` / `.internal` et IP privées refusés ; nom résolu, **toutes** les adresses doivent être publiques (même liste que les webhooks sortants, `isPrivateAddress`), connexion épinglée sur l’adresse validée ; 3 redirections au plus, chacune revalidée ; 8 s, 2 Mo (au-delà : tronqué + avertissement), `text/html` seulement. Conversion volontairement simple, sans DOM ni dépendance : `script|style|noscript|template|svg|iframe|object|canvas|video|audio|head…` supprimés avec leur contenu, éléments `hidden` / `display:none` / `aria-hidden` sautés ; seuls le texte, les `href` des boutons, les `src`/`alt` des images et les champs des formulaires sont lus → blocs `heading` (h1–h3), `text` (gras / italique conservés via `sanitizeRich`), `list`, `image` (URL absolue http(s), jamais `data:`), `button` (`<button>`, lien de classe `btn|button|cta` ou `role=button` ; lien `javascript:` → bouton « étape suivante »), `divider`, `form` (email, prénom, nom, téléphone ; l’`action` d’origine n’est pas reprise). 300 blocs max, liste plate, styles Scalo par défaut : ni mise en page, ni couleurs, ni CSS, ni scripts. Transport et DNS injectables (`setPageFetchDeps`).

### Paiements (Stripe)

Code : `api/src/services/stripe.ts` (passerelle), `services/payments.ts` (cycle de vie des commandes), `services/order-hooks.ts` (point d’extension), `routes/payments.ts` (session JWT), `routes/payments-public.ts` (pages publiques + webhook), `routes/v1-sales.ts` ; types partagés `shared/src/payments.ts`, rendu des blocs `shared/src/render-payments.ts`.

**Principes** — « Apportez votre Stripe » : chaque compte saisit ses propres clés ; l’argent arrive directement sur son compte Stripe. Le paiement a lieu sur **Stripe Checkout (page hébergée)** : SCA / 3-D Secure, moyens de paiement et reçus sont gérés par Stripe, **aucune donnée de carte ne transite par Scalo**, et le bon de commande reste un simple formulaire HTML (fonctionne sans JavaScript et dans les pages « sandbox »). Les montants sont **toujours recalculés côté serveur** à partir des offres en base (jamais lus dans la requête). Montants en centimes (entiers) ; devises à 2 décimales (`eur, usd, gbp, chf, cad, aud`). TVA simple : taux par offre, montant saisi TTC (`tax_inclusive`) ou HT (la TVA s’ajoute) — `computeAmounts()` ; Stripe reçoit le TTC.

**Passerelle** — le reste du code ne connaît que l’interface `StripeClient` (`retrieveAccount`, `createCheckoutSession`, `retrieveCheckoutSession`, `createOffSessionPayment`, `createRefund`, `cancelSubscription`), construite à partir de la clé du compte par une `StripeFactory`. Implémentation par défaut : API REST de Stripe via `fetch` (version d’API épinglée `2024-06-20`, clés d’idempotence, délai 20 s), sans dépendance npm. Les tests injectent un faux client : `createApp({ stripe: factory })` (`AppOptions.stripe`), aucun appel réseau. Les clés ne sont jamais journalisées ni renvoyées ; un message d’erreur Stripe qui en contiendrait une est masqué.

**Connexion** (`/api/payments/settings`) — clé secrète (`sk_|rk_` + `test|live`), clé publique (`pk_`, facultative), secret de signature du webhook (`whsec_`). Clé secrète et secret de webhook **chiffrés** en base (AES-256-GCM, `services/secretbox.ts` : clé dérivée par HKDF de `ENCRYPTION_KEY`, sinon de `JWT_SECRET` ; un espace de clés par usage) ; l’API ne renvoie que `*_hint` (4 derniers caractères). Mode test / réel déduit du préfixe (une clé publique d’un autre mode est refusée). Changer `ENCRYPTION_KEY` / `JWT_SECRET` rend les clés illisibles : l’API répond 409 « saisissez-les à nouveau ».

**Offres** — paiement unique ; abonnement mensuel / annuel ; **paiement en plusieurs fois** = abonnement mensuel arrêté automatiquement : à chaque `invoice.paid` on compte les paiements, au dernier l’abonnement est annulé chez Stripe et la commande passe `subscription_status = 'completed'` (l’acheteur garde le produit).

**Blocs de page** (`shared/src/content.ts`, palette « Vente ») :
- `checkout` (« Paiement ») `{offerId, submitLabel, askName?, askLastName?, showSummary?, secureNote?, bumpOfferId?, bumpTitle?, bumpText?, buttonBg?, buttonColor?, inputRadius?}` : bon de commande (prénom / nom / email) + **order bump** (case à cocher ; même devise que l’offre principale). `offerId` / `bumpOfferId` = ids d’offres ; nom et prix affichés viennent de la base au rendu (`RenderContext.offers`), `offerLabel` n’est que l’aperçu de l’éditeur. Offre inconnue, inactive, d’un autre compte ou Stripe non connecté → « offre indisponible ».
- `upsell` (« Offre en un clic ») `{offerId, acceptLabel, declineLabel?, note?, skipNextOnAccept?}` : bouton d’acceptation + lien de refus vers l’étape suivante (**downsell** = une étape suivante avec un autre bloc `upsell` ; `skipNextOnAccept` saute cette étape quand l’offre est acceptée).

**Pages publiques** (aussi servies sur les domaines personnalisés : `/<step>/checkout`…) :
- `POST /p/:funnel/:step/checkout` (form : `email, first_name?, last_name?, _block, bump?`) → crée la commande `pending` (lignes = instantané des offres, attribution UTM du cookie `scalo_src`, bras A/B, contexte visiteur) puis une session Checkout (`mode` `subscription` si une ligne est récurrente, sinon `payment` avec carte enregistrée `setup_future_usage=off_session`) et redirige (303) vers Stripe. Erreurs : retour sur l’étape avec `?pay=email|unavailable|error|preview|limit` (message affiché dans le bloc). 30 essais / 10 min par IP. Désactivé en aperçu.
- `GET /p/:funnel/:step/paid?session_id=…` (retour de Stripe) : interroge Stripe (pas besoin d’attendre le webhook), marque la commande payée, pose `scalo_cid` (contact) et `scalo_order` (commande signée, 24 h, limitée au tunnel) — seulement dans l’heure qui suit le paiement : l’URL de retour n’identifie pas l’acheteur au-delà — puis redirige vers l’étape suivante ; session encore ouverte → `?pay=cancel`.
- `POST /p/:funnel/:step/upsell` (form : `_block`) — **upsell en un clic** : exige le cookie `scalo_order` d’une commande payée depuis moins de 24 h. Offre à paiement unique : `PaymentIntent` `off_session` + `confirm` sur le client et la carte de la commande d’origine → commande `upsell` payée, redirection. **Repli** : authentification exigée par la banque (`authentication_required`), carte refusée, ou offre récurrente → session Checkout pour cette commande (client Stripe existant), retour par `/paid`. Une seule commande par (commande d’origine, offre) — verrou consultatif + clé d’idempotence Stripe : un double clic ne débite jamais deux fois.

**Commande payée** (`markOrderPaid`, une transaction, idempotent) : contact créé / complété (`upsertContact`, champs existants conservés), commande rattachée, paiement enregistré (`order_transactions`), `contacts.source` renseignée si vide ; pour chaque ligne : tag du produit (`addTag` → accès aux formations, campagnes déclenchées par tag), campagne du produit, événement `purchase` via `recordPurchase` (`{product, amount, currency, external_id: 'order:<id>:<ligne>', source: 'stripe'}` + tunnel / étape) → déclencheur d’automatisation « Achat » et condition de segment « a acheté » ; email de confirmation (envoi `kind = 'order'`, pré-rendu, envoyé par le worker même à un contact désinscrit : transactionnel) ; hooks `paid`.

**Webhook** — `POST /api/payments/webhook/:token` (URL propre au compte, à déclarer dans Stripe). Corps lu brut (`express.raw` monté avant le parseur JSON) ; signature `Stripe-Signature` vérifiée (HMAC-SHA256 de `<t>.<corps>` avec le secret du compte, tolérance 5 min, comparaison à temps constant) : invalide → 400, jeton inconnu → 404. **Idempotent** : l’id de l’événement est inséré dans `stripe_events` dans la même transaction que ses effets (rejeu → `{result: 'duplicate'}`, échec → 500 sans trace, Stripe réessaie) ; chaque effet est de plus idempotent sur l’objet Stripe (facture / payment intent). Événements : `checkout.session.completed` / `async_payment_succeeded` (session relue chez Stripe), `async_payment_failed`, `checkout.session.expired` (→ `canceled`), `payment_intent.succeeded` / `payment_failed` (via `metadata.order_id` ; une commande payée ne régresse jamais), `charge.refunded`, `invoice.paid` (renouvellements ; première facture d’une commande encore `pending` → payée), `invoice.payment_failed` (→ `past_due`), `customer.subscription.updated|deleted`. Les commandes sont toujours cherchées dans le compte de l’URL.

**Remboursements** — depuis l’UI (appel Stripe puis application immédiate) ou depuis Stripe (`charge.refunded`) : montant cumulé par paiement, donc les deux chemins ne se cumulent pas. Remboursement total → `refunded` et retrait du tag de chaque ligne si `revoke_on_refund` (option `revoke` pour forcer / empêcher), sauf si une autre commande payée du contact donne encore ce tag ; partiel → reste `paid`. Fin d’abonnement (annulation, impayé) → `subscription_status = 'canceled'` et même règle de retrait pour les lignes récurrentes.

**Point d’extension (affiliation, facturation…)** — `api/src/services/order-hooks.ts` :

```ts
type OrderHookEvent = 'paid' | 'subscription_payment' | 'refunded' | 'subscription_canceled';
interface OrderHookContext { event: OrderHookEvent; order: OrderRow; items: OrderItemRow[]; amount: number; full?: boolean }
type OrderHook = (ctx: OrderHookContext, trx: Db) => Promise<void> | void;
function registerOrderHook(name: string, hook: OrderHook): () => void;              // retourne la fonction de retrait
function onOrderPaid(name: string, fn: (order: OrderRow, trx: Db, ctx: OrderHookContext) => Promise<void> | void): () => void;
function onOrderRefunded(name: string, fn: (order: OrderRow, trx: Db, ctx: OrderHookContext) => Promise<void> | void): () => void;
```

Un hook s’exécute **dans la transaction** qui change la commande (ce qu’il écrit est validé avec elle, exactement une fois par événement), chacun dans son `SAVEPOINT` : un hook qui échoue est annulé et journalisé, il ne bloque ni le paiement ni les autres hooks. `amount` = centimes encaissés (`paid`, `subscription_payment`) ou remboursés par cet événement (`refunded`, `full` = commande entièrement remboursée). `order` est la ligne `orders` après changement (`contact_id`, `funnel_id`, `step_id`, `parent_order_id`, `amount_paid`, `amount_refunded`, `attribution`…). Le **contexte visiteur** est conservé dans `orders.visitor` : `{visitor_id, cookies}` où `cookies` contient les cookies du visiteur dont le nom correspond à `VISITOR_COOKIE_RE` (`scalo_aff*`, `scalo_ref*`, ≤ 300 caractères, 10 max) au moment de la commande — une extension d’affiliation pose par exemple `scalo_aff` sur son lien et le relit ici (les upsells héritent du contexte de la commande d’origine). Les hooks ne doivent pas appeler de service externe (la ligne de la commande est verrouillée).

### Affiliation

Programme d’affiliation du cœur (AGPL, rien dans `ee/`), branché sur les paiements par le hook de commande `affiliates`. Code : `api/src/services/affiliates.ts` (programme, cookie, clics, leads, commissions, paiements), `services/affiliate-pages.ts` (HTML de l’espace affilié), `routes/affiliates.ts` (admin, session JWT, `/api/affiliation/…`), `routes/affiliate-space.ts` (espace public `/a/<slug>`, monté avant `publicRouter`) ; types `shared/src/affiliates.ts` ; front `web/src/pages/affiliates/`, client `web/src/lib/affiliates-api.ts` ; tests `api/test/affiliates.test.ts` ; guide `docs/affiliation.md`.

- **Schéma** (`0012_affiliates`) : `affiliate_programs` (PK `user_id` `CASCADE` ; `enabled` (défaut non), `slug` unique global (adresse `/a/<slug>`), `name`, `commission_type` `percent|fixed` + `commission_value numeric(12,2)` (défaut 30 % ; `CHECK` ≤ 100 en pourcentage), `recurring` (défaut oui) + `recurring_months` 1–120 nullable, `cookie_days` 1–365 (30), `attribution` `last_click|first_click`, `validation_days` 0–365 (30), `min_payout` (centimes), `signup_mode` `open|approval`, `terms` ≤ 20 000) ; `affiliates` (compte et contact `CASCADE`, `UNIQUE (user_id, contact_id)`, `code` `^[a-z0-9][a-z0-9-]{1,30}[a-z0-9]$` unique par compte, `status` `pending|approved|rejected|suspended`, `commission_type` / `commission_value` nullables ensemble, `payout_details_enc` (chiffré), `approved_at`) ; `affiliate_commission_rules` (`product_id` `CASCADE`, `price_id` nullable `CASCADE`, taux ; unique `(user_id, product_id, COALESCE(price_id, 0))`) ; `affiliate_clicks` (`affiliate_id`, `visitor_id`, `day date`, tunnel / étape `SET NULL` ; `UNIQUE (affiliate_id, visitor_id, day)` ; ni IP ni user agent) ; `affiliate_referrals` (`kind` `lead|sale`, `contact_id` `SET NULL`, `order_id` `CASCADE` ; index uniques partiels : une commande → un affilié, un contact → lead d’un seul affilié) ; `affiliate_payouts` (`affiliate_id`, `currency`, `amount > 0`, `method`, `reference`, `note`) ; `affiliate_commissions` (registre : `affiliate_id`, `order_id` / `order_item_id` `SET NULL`, `kind` `sale|recurring|clawback`, `source_key`, `reverses_id`, `product_name`, `currency`, `base_amount` (HT encaissé), `rate_type` / `rate_value`, `amount_initial`, `amount`, `status` `pending|approved|paid|cancelled`, `approve_at`, `approved_at`, `payout_id` `SET NULL`, `paid_at`, `cancelled_at`, `cancel_reason` ; `CHECK` de signe (reprise ≤ 0, sinon ≥ 0) ; index uniques partiels `(order_id, order_item_id, source_key)` hors reprises et `(reverses_id, source_key)` pour les reprises = **idempotence** ; index partiel `(approve_at) WHERE status = 'pending'` pour le worker). Types d’événements `affiliate_joined`, `affiliate_commission` et déclencheur d’automatisation `affiliate_approved` : les `CHECK` `contact_events.type` et `automations.trigger_type` sont reconstruits à partir de leurs valeurs actuelles. Le `down` supprime les tables, ces événements et les automatisations de ce déclencheur.
- **Lien et cookie** : `?aff=<code>` sur toute page de tunnel (`viewStep`, donc `/p/<tunnel>/<étape>` et domaines personnalisés ; `GET /p/<tunnel>` conserve le paramètre dans sa redirection). Hors aperçu, programme activé et code bien formé : cookie **`scalo_aff_<id du compte>`** (un par compte, plusieurs comptes partageant l’hôte de l’application ; correspond à `VISITOR_COOKIE_RE`), `HttpOnly`, `SameSite=Lax`, `Path=/`, `Max-Age` = durée du cookie. Valeur = `{c: code, t: horodatage du clic}` chiffré et authentifié (AES-256-GCM, `services/secretbox.ts`, clé dérivée par compte : `affiliate:cookie:<id>`) : illisible, infalsifiable, sans valeur pour un autre compte. **Dernier clic** : un code valide remplace le cookie ; **premier clic** : le cookie encore valable d’un affilié toujours approuvé est conservé. Le code de l’URL est une donnée non fiable : un code inconnu (ou d’un affilié non approuvé) reçoit la même réponse qu’un code valide — un cookie opaque (qui conserve l’attribution existante s’il y en a une, sinon ne mène nulle part) — donc **pas d’énumération** des affiliés. **Clic** : une ligne par (affilié, visiteur `scalo_vid`, jour), `ON CONFLICT DO NOTHING`. L’expiration est revérifiée côté serveur à la commande (date du clic + `cookie_days` ≥ date de création de la commande).
- **Lead** : à la soumission d’un formulaire de tunnel (`submitStep`, dans sa transaction), le contact devient le lead de l’affilié du cookie (`affiliate_referrals`, `kind = 'lead'`), une seule fois par contact, jamais de lui-même ; statistique sans commission.
- **Commissions** (hook `affiliates`, dans la transaction de la commande) — `paid` : l’affilié de la commande est décidé une fois (`affiliate_referrals`, `kind = 'sale'`) : celui de la **commande d’origine** pour un upsell, sinon celui du cookie copié dans `orders.visitor.cookies` ; refusé si l’affilié n’est pas approuvé ou si l’acheteur est l’affilié lui-même (même contact, ou même email sans casse ni suffixe `+alias`). Pour chaque ligne : base = part **hors taxes** du montant encaissé (`amount × ligne.amount_subtotal / Σ amount_total des lignes payées`), taux = règle de l’offre, sinon du produit, sinon commission de l’affilié, sinon du programme (`resolveRate`) ; montant = `round(base × % / 100)` ou le fixe plafonné à la base ; aucune ligne à 0 (commande gratuite, taux 0 %). Commission créée `pending`, `approve_at = maintenant + validation_days`, `source_key = 'tx:<id du paiement>'`. `subscription_payment` : mêmes règles pour les lignes récurrentes — abonnements si `recurring` (et dans la limite de `recurring_months` après `paid_at`), **paiements en plusieurs fois toujours** ; `kind = 'recurring'`. Programme désactivé ou affilié suspendu : aucune commission (renouvellements compris). Événement `affiliate_commission {amount, currency, product, order_id, recurring}` sur la fiche de l’affilié.
- **Remboursements** (hook, événement `refunded`) : commissions de la commande non payées (`pending` / `approved`) → `cancelled` si le remboursement est total, sinon réduites de `amount_initial × remboursé / amount_paid` (annulées si elles tombent à 0). Commissions déjà **payées** → ligne `clawback` négative (`status = 'approved'` immédiatement, `reverses_id`, `source_key = 'refund:<cumul remboursé>'`), plafonnée au montant payé : le solde payable baisse, éventuellement sous zéro, et se compense sur les commissions suivantes.
- **Validation** : `approveDueCommissions()` appelée par le worker à chaque tour (`runSchedulers`) passe `pending → approved` quand `approve_at` est dépassé (UPDATE conditionnel, sans risque entre plusieurs instances).
- **Paiements aux affiliés** : registre manuel, aucun virement. `createPayout` (transaction, lignes verrouillées) marque `paid` toutes les commissions `approved` de l’affilié dans la devise, reprises comprises ; refusé (409) si le solde n’est pas positif ou sous `min_payout`. Soldes par affilié et devise : `pending`, `approved` (à payer, peut être négatif), `paid`.
- **Espace affilié** (`/a/<slug>`, SSR, `Cache-Control: no-store`, `noindex`, CSP `default-src 'none'` + script limité par nonce au bouton « Copier », `frame-ancestors 'none'`, formulaires refusés depuis une autre origine) : page du programme + inscription, connexion, tableau de bord (clics, leads, ventes, conversion, commissions en attente / validées / payées, 100 dernières commissions, paiements reçus), générateur de liens (pages publiques des tunnels, domaine personnalisé vérifié sinon `PUBLIC_URL/p/…`), coordonnées de paiement, conditions. **Authentification = celle de l’espace membres** (`services/members.ts`) : jeton à usage unique haché dans `member_login_tokens` (20 min, GET = bouton, POST = consommation), session `signSession` / `verifySession` liée au compte, cookie `scalo_affiliate` `HttpOnly` limité à `/a/<slug>` ; 10 demandes / 15 min par IP (429), 3 emails / 15 min par adresse (silencieux), réponse identique que l’adresse soit connue ou non. **Inscription** : le contact est créé si besoin (non confirmé : pas d’abonnement aux emails du compte) et l’affilié n’est créé qu’à l’utilisation du lien (`pending`, ou `approved` si `signup_mode = 'open'`). Toutes les requêtes du tableau de bord sont filtrées par l’id de l’affilié connecté ; l’identité des acheteurs n’est jamais affichée. **Coordonnées de paiement** : texte libre ≤ 1000, chiffré (`secretbox`, usage `affiliate:payout-details`), lisible par l’affilié et par les propriétaire / administrateurs du compte seulement.
- **Rôles** : `payouts` est ajouté aux sous-zones d’administration de `api/src/access.ts` — un éditeur ne peut écrire ni sur `/affiliation/settings` ni sur `/affiliation/payouts…` ; en plus, les routes réservent aux propriétaire / administrateurs la commission personnalisée d’un affilié, l’annulation manuelle d’une commission et la lecture des coordonnées de paiement (détail d’un affilié, export CSV).

- `POST /p/:funnelSlug/:stepSlug/submit` (form urlencoded: `email, first_name, last_name, phone, _block`) → crée ou met à jour le contact du propriétaire du funnel, event `optin`, applique `tagName` du bloc formulaire (`_block`), inscrit à `campaignId` si défini, pose le cookie `scalo_cid`, redirige (303) vers l'étape suivante. Email invalide → redirige vers la même page avec `?error=email`.

### Accès aux étapes
`PATCH /api/steps/:id` accepte `access: {mode: 'public'|'funnel'|'tag'|'password', tag_id?, redirect?: 'first'|'previous'|'url', redirect_url?, password?}`.
- `funnel` : visiteur inscrit via un formulaire de ce tunnel (cookie signé `scalo_cid` + optin dans le tunnel) ; `tag` : contact identifié ayant le tag ; `password` : formulaire `POST /p/:f/:s/unlock` (bcrypt, cookie signé 30 j, 10 essais / 15 min / IP et étape, compteur en base `auth_attempts`, 429 + `Retry-After`).
- Refus : redirection vers la 1re (ou la précédente) étape **publique**, ou une URL ; sinon page 403. Pages protégées : `X-Robots-Tag: noindex`. Les formulaires d'une étape protégée refusent les soumissions non autorisées.
- Aperçu propriétaire : `Step.preview_url` contient `?preview=<jeton signé>` valable 24 h pour tout le tunnel, qui contourne les règles ; `?preview=1` ne fait que désactiver le comptage des vues.

Inscription campagne : pour chaque email de la campagne (par position), un `email_send` (`kind='campaign'`) est créé avec `send_at` = inscription + somme cumulée des `delay_days`. Un contact n'est inscrit qu'une fois par campagne (et pas s’il n’a pas confirmé son double opt-in — il l’est à la confirmation — ni s’il a déjà le tag d’arrêt).
Évaluation **à l’échéance** (worker, `services/campaigns.ts`) : inscription arrêtée / désinscrite → `skipped` ; tag d’arrêt → inscription `stopped` et envois restants `skipped` ; un email précédent de la séquence encore `pending`/`sending` → report (sans compter de tentative) ; condition fausse → `skipped` (`skip`) ou arrêt de la séquence (`stop`). « Email précédent » = dernier email de la campagne réellement envoyé au contact. L’inscription passe `completed` quand plus rien n’est en attente (et redevient `active` si un email est rattrapé).
Rattrapage (`apply_to_existing`) à l’ajout d’un email : pour chaque inscrit actif, échéance = inscription + délais cumulés ; déjà passée → envoyé maintenant (+10 min pour laisser le temps de rédiger) si `true`, ignoré si `false` ; à venir → programmé normalement dans les deux cas. Index unique partiel `(campaign_email_id, contact_id)` : jamais deux fois. Réordonner / changer un délai / supprimer un email recalcule `send_at` des envois en attente jamais tentés.
Écart assumé : les envois sont créés à l’inscription (modèle « pré-matérialisé », compatible avec le contrat et les tests existants) mais tout ce qui dépend de l’état du contact est évalué à l’échéance, ce qui donne le même résultat qu’une matérialisation paresseuse pour le rattrapage, l’ordre, les conditions et l’arrêt.

### Envoi & tracking
Moteur d'envoi ([api/src/worker.ts](api/src/worker.ts)), tick 1 s, **sûr en multi-instance** (plusieurs processus API sur la même base) :
- **Débit** : seau à jetons par compte à `rate_per_minute` (défaut 60, petite rafale ~2 s) + `daily_limit` optionnel sur 24 h glissantes. Le seau à jetons et le backoff sont en mémoire **par processus** : avec N instances, un compte peut ponctuellement envoyer jusqu'à N× son débit. La limite quotidienne est calculée en base, donc partagée.
- **Réservation atomique** `pending → sending` avant envoi : `UPDATE email_sends SET status='sending', attempts=attempts+1, last_attempt_at=now(), claimed_by=<instance> WHERE id IN (SELECT … ORDER BY (broadcast_id IS NOT NULL), send_at, id LIMIT n FOR UPDATE SKIP LOCKED) RETURNING …`. Deux processus (ou deux ticks) ne réservent jamais la même ligne ; un envoi n'est donc jamais traité deux fois.
- **Reprise après crash** : chaque processus s'inscrit dans `worker_instances` (battement toutes les 10 s, supprimé à l'arrêt propre). Les lignes `sending` dont l'instance n'a plus donné signe de vie depuis 30 s (ou arrêtée) sont récupérées par n'importe quelle instance vivante (au démarrage puis toutes les 30 s) : `failed` avec SMTP réel (pour éviter un doublon ; relançables à la main), de nouveau `pending` en mode dev. Les envois en cours d'une instance vivante ne sont jamais touchés.
- **Arrêt propre** (SIGINT/SIGTERM) : fin des nouveaux ticks, attente des livraisons en cours (20 s max), fermeture du serveur HTTP, des connexions SMTP et du pool PostgreSQL.
- **Priorité** : emails de confirmation (double opt-in) d’abord, puis emails de campagne, puis newsletters, puis par `send_at`.
- **Planification** (à chaque tick, avant la réservation) : newsletters programmées dues (`UPDATE broadcasts SET status='sent' WHERE id=? AND status='scheduled' AND scheduled_at <= now() RETURNING` + insertion des envois dans la même transaction) et tests A/B dont l’attente est finie (`UPDATE … SET ab_phase='done' WHERE ab_phase='testing' AND ab_decide_at <= now() RETURNING`, choix du gagnant, envoi au reste des destinataires — `ON CONFLICT DO NOTHING`). Sûr en multi-instance : la ligne verrouillée par l’UPDATE du premier est ignorée par les autres.
- **Contrôles à l’envoi** : contact introuvable / bounce → `failed` ; désinscrit → `failed` (`unsubscribed`) ; non confirmé → `skipped` ; confirmation : envoyée telle que rendue à la demande (lien à usage unique, sans tracking), bloquée par bounce, plainte ou désinscription postérieure à la demande.
- **SMTP** : connexion poolée par compte (2 connexions, recyclée tous les 100 mails), version texte auto, en-têtes `List-Unsubscribe` + `List-Unsubscribe-Post` (one-click RFC 8058), `X-Scalo-Send-Id`, `Feedback-ID: <b123|c45|kind>:<compte>:<kind>:scalo` ; le `Message-ID` renvoyé est stocké (`email_sends.message_id`) pour relier les webhooks.
- **Erreurs** : temporaire (4xx) → nouvelle tentative à +1 min, +5 min, +30 min (4 tentatives max) ; connexion/421 → compte en `backoff` 60 s ; adresse rejetée (5xx RCPT) → échec + contact `bounced` exclu des envois ; authentification refusée → file mise en pause avec `paused_reason`.
- Sans SMTP : **mode dev**, les mails sont marqués `sent` et lisibles dans le suivi.
- **Plaintes / rebonds** (`POST /api/webhooks/email/:provider/:secret`, public, `provider` ∈ `generic|ses|postmark|mailgun|brevo`, 404 si secret ou fournisseur inconnu, 400 si format non reconnu) : générique `{type: 'complaint'|'bounce', email, message_id?, send_id?}` (ou tableau) ; SES via SNS (corps `text/plain` accepté ; `SubscriptionConfirmation` confirmée par `GET SubscribeURL` seulement si `https://sns.<région>.amazonaws.com[.cn]`, sinon 400 ; `Notification` → `Complaint`, `Bounce` `Permanent`) ; Postmark (`SpamComplaint`, `Bounce` durs) ; Mailgun (`complained`, `failed` + `permanent`) ; Brevo (`spam`/`complaint`, `hard_bounce`/`invalid_email`). Envoi retrouvé par `X-Scalo-Send-Id`, puis `message_id`, puis dernier envoi à l’adresse. Plainte → `contacts.complained` + désinscription, envois en attente annulés, inscriptions de campagne `unsubscribed`, `email_sends.complained_at`, event `spam_complaint` ; bounce → comme un 5xx SMTP. Pause automatique si plaintes > 0,3 % des 1 000 derniers envois (dès 100 envois). `fetch` injectable (`createApp({fetch})`). Signature SNS non vérifiée (le secret de l’URL authentifie).
- Endpoints : `GET /api/emails/queue` (`QueueStatus` + `upcoming` : newsletters programmées, `complaints` : taux de plaintes 30 j et sur les 1 000 derniers envois, `jobs[].ab_phase/ab_decide_at`), `POST /api/emails/queue/pause|resume`, `POST /api/emails/queue/retry-failed {broadcast_id?}`, `POST /api/emails/queue/cancel {broadcast_id}`, `POST /api/emails/sends/:id/retry`, `GET /api/emails/outbox?status=(pending|sending|sent|failed|skipped)&broadcast_id=&search=` (items + `kind`, `variant`, `source` `confirmation`), `POST /api/settings/test-smtp`.
- `GET /t/o/:id.gif` → GIF 1x1, `opened_at`. `GET /t/c/:id?u=` → `clicked_at` (+ opened), redirect 302 (uniquement vers une URL présente dans le mail). `GET /u/:token` → page de confirmation ; `POST /u/:token` → désinscription (formulaire ou one-click).

- **Contrat `EeApi`** (retourné par `register()` de `ee/api/src/index.ts`) : `resolveActor(userId)` → `{accountId, role}` ou `null` ; `publicRouter` (monté sous `/api` avant l’authentification par `editionPublicGate()`, qui charge aussi l’extension) ; `router` (après `requireAuth`, via `editionGate()`) ; `onRequest(req, res)` (journal d’audit) ; `poweredBy(accountId)` (synchrone) ; `edition(accountId)` ; `cleanup()` (appelé par le ménage périodique d’`index.ts`).
- **`requireAuth`** (`api/src/util.ts`) : après la vérification du JWT, `req.userId = req.actorId = id`, `req.role = 'owner'`. Si l’extension est chargée : `resolveActor` peut remplacer `req.userId` (le compte pour lequel la personne agit) et `req.role` ; puis `onRequest` ; puis la règle de rôle → 403 `{error}`. Sans extension, ou pour un compte sans équipe : comportement identique à avant. `GET /api/auth/me` renvoie la personne connectée (`req.actorId`).
- **Règle de rôle** (`roleAllows(role, method, path)`, générique — pas une liste de routes, donc valable pour toute route ajoutée) : `owner` tout ; `admin` tout sauf les écritures sur `/account` et `/license` ; `editor` : lectures + écritures hors zones d’administration (premier segment `settings|billing|team|license|audit|branding|developer|oauth|account|api-keys|integrations`, second segment `settings|billing|api-keys|key|keys|credentials|connect|payouts`, ou dernier segment `refund|cancel-subscription`), et aucune lecture sur `billing|team|audit|developer|oauth|api-keys` ; `viewer` : `GET/HEAD/OPTIONS` hors ces mêmes zones de lecture réservée, plus les `POST` de pure lecture `/segments/preview`, `/contacts/query`, `/preview/email`.
- **`GET /api/edition`** (cœur, session) → `EditionInfo` `{edition: 'community'|'enterprise', license: {status: 'none'|'valid'|'grace'|'expired'|'invalid', plan, features, seats, expires_at, grace_until}, features (actives), role, actor: {id, name, email}, account: {id, name, email}, branding: {app_name, logo_url} | null}` (`shared/src/edition.ts`). Édition communautaire : `community`, `owner`, licence `none`.
- **Mention « Propulsé par Scalo »** (`api/src/services/branding.ts`) : pied discret des pages publiques (`<div data-scalo-powered>`, lien vers `https://scalo.fr`, ajouté à `bodyEnd`) et dernière ligne du pied des emails (texte sans lien, donc rien à réécrire par le suivi des clics). Seule l’extension peut la retirer ou la remplacer pour un compte.
- **Schéma** (`0011_ee`) : `account_members` (`account_id` → users `CASCADE`, `user_id` → users `CASCADE` **unique** — un membre appartient à un seul compte —, `role` `admin|editor|viewer`, `invited_by` `SET NULL`, `CHECK account_id <> user_id`) ; `account_invitations` (`email` en minuscules, `role`, `token_hash` SHA-256 unique, `expires_at`, `accepted_at`, index unique partiel `(account_id, email) WHERE accepted_at IS NULL`) ; `audit_logs` (`account_id` `CASCADE`, `actor_id` `SET NULL` + `actor_email` / `actor_role` figés, `action`, `method`, `path`, `resource_type`, `resource_id`, `status`, `ip`, `created_at` ; index `(account_id, id DESC)`, `(created_at)`) ; `account_ee_settings` (PK `account_id`, `hide_powered_by`, `powered_by_text` ≤ 80, `powered_by_url` http(s), `app_name` ≤ 40, `logo_url` `https://` ou `/uploads/`, `audit_retention_days` 1–3650 défaut 365) ; `instance_license` (ligne unique : `license_key`, `updated_by`). Le `down` supprime ces tables ; les membres restent des comptes `users` ordinaires.
- **Édition Entreprise** (résumé, voir `ee/README.md`) : licence = jeton `scalo_lic_<contenu>.<signature>` signé Ed25519, vérifié hors ligne (clé publique embarquée dans `ee/api/src/license/keys.ts`), fourni par `SCALO_LICENSE_KEY` ou Paramètres → Licence ; grâce de 14 jours après expiration ; `license.has('team'|'audit_log'|'white_label')` ; routes `/api/license`, `/api/team…`, `/api/invitations/:token[/accept]` (publiques), `/api/audit…`, `/api/branding` ; 402 quand la fonction demande une licence. Une licence absente, invalide ou expirée ne bloque jamais le cœur ni les données.
- **Front** : `web/src/lib/edition.tsx` (`EditionProvider`, `useEdition()` : `info`, `role`, `has(feature)`, `isAdmin`) ; le logo du menu suit `branding` ; quand `ee/` est installé, Paramètres gagne les sections Équipe, Journal d’audit, Marque blanche et Licence (écran sobre « Fonction de l’édition Entreprise » sans licence), un bandeau discret signale l’expiration de la licence (propriétaire et administrateurs) et le rôle lecture seule, et `/invite/:token` permet d’accepter une invitation.

## Modèle de contenu (`shared/src/content.ts`)

`PageContent = { settings: PageSettings, blocks: Block[] }`. Les blocs forment un **arbre** : `section.children: Block[]`, `columns.columns[]: { id, width, children, background?, padding? }` (1 à 4 colonnes, largeurs relatives). Un ancien contenu « plat » est un arbre valide et s'affiche à l'identique. Profondeur max rendue : 6.

- Blocs : `heading, text, list, image, button, form, video, spacer, divider` (historiques) + `section, columns, countdown, testimonial, pricing, faq, feature, social, imageText, progress, navbar, footer, html, rating, quote` + paiements (pages uniquement) : `checkout`, `upsell` (voir « Paiements »).
- `style: BlockStyle` commun : `align, color, background, paddingTop/Bottom (ou paddingY historique), paddingX, marginTop/Bottom, fontSize, mobileFontSize, fontWeight, lineHeight, letterSpacing, borderWidth/Color/Radius, shadow (sm…xl), hideOnMobile, hideOnDesktop`.
- `PageSettings` : couleurs, `maxWidth`, `fontFamily`, `headingFont` (Google Fonts chargées par `<link>` sur la page et dans l'éditeur), `contentPadding` ; page : `seoTitle, seoDescription, ogImage, favicon, headCode` ; email : `preheader`.
- Texte riche : markdown-lite historique (`**gras**`, `*italique*`, `[lien](url)`) **ou** HTML filtré par liste blanche stricte (`sanitizeRich` : b/strong/i/em/u/s/br, a[href http(s)/mailto/tel/relatif], span[style=color]). L'éditeur stocke via `normalizeRich`.
- Rendu (`shared/src/render.ts`) : `renderBlock / renderPageDocument / renderEmailDocument` (signatures inchangées, `baseUrl` optionnel ; `renderPageDocument` accepte aussi `headExtra` / `bodyEnd`, HTML généré par le serveur : pixels, bandeau cookies, pied de page légal). Page : `<style>` avec media queries (empilement des colonnes < 640 px, masquage mobile/ordinateur, taille mobile), script inline minimal pour les comptes à rebours. Email : tables uniquement, boutons « bulletproof », colonnes en `<td class="scalo-col">` empilées par media query, preheader caché, pas de formulaire / HTML / compte à rebours dynamique, FAQ dépliée.
- Bloc `html` et `headCode` : uniquement sur la page publique du propriétaire ; la page est alors servie avec `Content-Security-Policy: sandbox allow-scripts allow-forms …` (origine opaque : le code ne peut pas lire la session de l'app). Dans l'éditeur : aperçu `iframe sandbox=""`.
- Modèles (`shared/src/library.ts`) : `PAGE_TEMPLATES` (7), `EMAIL_TEMPLATES` (4), `SECTION_TEMPLATES` (bibliothèque de sections). Arbre : helpers immuables dans `shared/src/tree.ts`.
